## What this is

A controlled development system in which coding agents work inside defined
roles, use approved tools, produce evidence, and cannot bypass quality
gates. GitHub is the system of record; `.ai/` is the canonical,
provider-neutral source. The user's full plan (phases 0–9, 15 first cards)
is summarized in the MAGPIE-AGENT-01 card in the Inbox of `.ai/KANBAN.md`.

## Standing rules from the user

- **One small card at a time** (vault `AGENTS.md`): Inbox → Research → Ready
  → In Progress → Review → Done. Only the coordinating agent moves cards.
  Write the card before changing code; record evidence before Review; the
  user accepts before Done. End each card with a short review packet and one
  suggested next card.
- **Tests first:** write the tests, record the failing run, then implement.
- **Reuse first, pay last:** existing code → open source → build → paid.
  Always the cheapest viable option; paid needs a named human approver.
  Applies to this project's own tool choices too.
- **Readable code:** plain English names, small units, comments only for
  "why" (vault `AGENTS.md`).
- **Communication:** ADHD-friendly — say what is happening now, show one
  next decision, no large backlog dumps. The user may write in Finnish.

## Design decisions worth knowing

- Never-grantable capabilities (merge, self-approval, branch-protection
  changes, disabling security workflows, suppressing or downgrading
  findings, committing to paid services) are hard-coded in
  `tools/validate_constitution.py`, not in the manifest, so editing the
  manifest alone cannot grant them. Every role must also deny them
  explicitly.
- Principle changes need a version bump, a change-history row in
  `constitution.md`, and the user's approval.
- Card conventions: `## ` sections, Gherkin in a ```gherkin block, at least
  one `@failure` scenario, a traceability table with header
  `Acceptance criterion | Test | Result`, and `Decision:` /
  `Alternatives checked:` / `Approved by:` lines under `Reuse and cost`.
- GitHub issue forms (YAML) were rejected: they emit `###` headings and
  "_No response_", which would not match the card validator. Markdown issue
  templates are used instead.
- `.github/` templates are generated; edit `.ai/templates/` and regenerate.
  The workflow file is hand-written.
- The workflow passes PR text to shell only through environment variables
  (script-injection protection); its permissions are read-only.

## Open risks and gaps

- Nothing is enforced on GitHub yet: no repository exists, and the
  AGENT-OS-05 ruleset must be applied by the user with the `gh api` command
  in the README (public repository on the free plan). Until then a failing
  check could still be merged around.
- Workflow actions are pinned to major tags (`@v4`, `@v5`), not commit SHAs.
- The workflow has never run on GitHub; `actionlint` was not available.
- Editing only the issue does not re-run the PR gate.
- The "Then describes an implementation detail" check is a word list.
- Traceability checks that a test location is named, not that the test
  exists or passed.
